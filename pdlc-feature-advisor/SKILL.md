# PDLC Feature Advisor

기존 서비스를 분석해 "왜 이 기능이 이 서비스에 필요한가"를 근거와 함께 제안한다. 아이디어 나열이 아닌 **문제→해결 연결**이 핵심이다. 근거 없는 제안은 출력하지 않는다.

## 입력 우선순위

아래 순서로 읽을 수 있는 것을 최대한 읽는다. 많이 읽을수록 제안 품질이 높아진다.

1. `docs/02-requirements/personas.md` — 누구의 문제인지
2. `docs/02-requirements/brd.md` — 이미 확정된 요구사항 (중복 제안 방지)
3. `docs/01-process-analysis.md` — Pain Point 목록 (PP-###)
4. `docs/03-spec/functional-spec.md` — 현재 구현된 기능 (FEAT-###)
5. `docs/07-ops/ops-issues.md` — 운영 중 발견된 실제 문제
6. `src/` 코드베이스 — 위 문서가 없을 때 코드에서 직접 서비스 구조 파악
7. 사용자가 구두로 설명한 서비스 개요 — 아무것도 없을 때 최소 입력

**문서가 하나도 없으면:** 사용자에게 최소 3가지를 질문한다.
- 서비스 한 줄 정의 (무엇을 누구에게)
- 현재 핵심 기능 2~3개
- 가장 개선하고 싶은 지표 (리텐션 / 전환율 / 객단가 / 바이럴 / 기타)

## 워크플로우

### 1. 서비스 맥락 파악

읽은 문서와 코드에서 아래를 추출한다.

- **도메인 분류**: 커머스 / 소셜 / 생산성 / 콘텐츠 / 예약·매칭 / 핀테크 / 헬스 / 기타
- **현재 핵심 기능 목록** (FEAT-### 또는 코드에서 추출)
- **확인된 Pain Point** (PP-### 또는 운영 이슈에서)
- **유저 페르소나** (이름, 목표, 주요 불만)
- **개선 목표 지표**: 사용자가 밝혔거나 Pain Point에서 추론

### 2. 유저 여정 갭 분석

현재 기능들로 페르소나의 여정을 추적한다. 여정은 아래 단계로 구성된다.

```
인지 → 가입/진입 → 첫 핵심 행동 → 반복 사용 → 심화 참여 → 추천/공유
```

각 단계에서 "현재 서비스가 지원하는가"를 판단한다. 지원이 약하거나 없는 단계 = 제안 대상.

### 3. 도메인 패턴 적용

`references/domain-patterns.md`에서 해당 도메인의 검증된 패턴을 읽는다. 패턴을 갭과 교차해 후보 기능 목록을 만든다.

**필터 기준 — 아래 조건을 하나도 충족하지 않으면 제안하지 않는다:**
- 기존 Pain Point(PP-###) 또는 운영 이슈(OPS-###)와 연결되는가
- 페르소나의 목표 달성을 직접적으로 돕는가
- 동일 도메인 검증 사례(레퍼런스 서비스)가 존재하는가

### 4. 제안 작성

각 제안을 아래 형식으로 작성한다. 형식을 지키지 않으면 하류에서 REQ로 전환할 수 없다.

```markdown
### FEAT-IDEA-### | [기능명]

**한 줄 정의:** [무엇을 하는 기능인가]

**타깃 문제**
- 연결 Pain Point: PP-### ([Pain Point 내용])
- 영향받는 페르소나: [페르소나명] — [이 페르소나에게 왜 필요한가]
- 유저 여정 갭: [어느 단계에서 지원이 부족한가]

**근거**
- 검증 사례: [레퍼런스 서비스명] — [어떤 효과가 있었는가]
- 기대 효과: [구체적 지표 변화 가설, 예: "재방문율 +15~25% 예상"]

**구현 개요**
- 핵심 동작: [사용자가 하는 행동 → 시스템이 하는 일]
- 필요 데이터: [새로 필요한 테이블/필드]
- 기존 기능 의존: FEAT-### (있는 경우)

**평가**
- 영향 지표: 리텐션 / 전환율 / 객단가 / 바이럴 / 운영효율 (해당하는 것)
- 구현 난이도: Easy(1~2일) / Medium(3~5일) / Hard(1주+)
- 우선순위 점수: [Impact 1~5] × [Effort 역수 1~5] = [총점]
```

### 5. 제안 요약표 출력

모든 제안을 우선순위 순으로 정렬한 요약표를 마지막에 출력한다.

```markdown
## 제안 요약 (우선순위 순)

| ID | 기능명 | 타깃 지표 | 난이도 | 우선순위 점수 | 연결 PP |
|----|--------|-----------|--------|--------------|---------|
| FEAT-IDEA-001 | ... | 리텐션 | Medium | 20 | PP-003 |
| FEAT-IDEA-002 | ... | 전환율 | Easy | 18 | PP-007 |
```

### 6. 파이프라인 편입 안내

제안 출력 후 사용자에게 묻는다:

> "위 제안 중 다음 스프린트에 넣을 기능을 선택하면 BRD(2단계)에 REQ로 편입하거나, 바로 기능명세(3단계)로 확장할 수 있습니다. 어떤 기능을 진행할까요?"

선택받으면:
- `docs/pipeline-state.json`의 `decisions` 배열에 선택 기록 추가
- 선택한 FEAT-IDEA를 REQ-### 형식으로 변환해 `docs/02-requirements/brd.md`에 추가 (파일이 있는 경우), 또는 새 파일로 생성
- `stale: true` 플래그를 영향받는 하류 단계(3·4·5단계)에 설정

## 제안 수 기준

- **최소 3개, 최대 7개**. 10개를 뿌리는 것은 브레인스토밍이다.
- 근거 없이 숫자를 채우지 않는다. 근거 있는 3개가 근거 없는 7개보다 낫다.
- 유저 여정의 여러 단계를 커버하도록 분산한다 (같은 단계만 3개 몰리지 않도록).

## 우선순위 점수 계산

```
Impact (1~5):
  5 = 핵심 지표에 직접 영향, 다수 페르소나 해당
  3 = 보조 지표 또는 일부 페르소나
  1 = 간접적, 소수 해당

Effort 역수 (1~5):
  5 = Easy (1~2일)
  3 = Medium (3~5일)
  1 = Hard (1주+)

우선순위 점수 = Impact × Effort역수
```

## 출력 언어 규칙

본문 한국어. 기능명·지표·레퍼런스 서비스명은 영어 병기 허용. 코드·SQL은 영어.

## 완료 기준 (자체 체크)

- [ ] 서비스 도메인 분류 명시
- [ ] 유저 여정 갭 분석 결과 서술
- [ ] 모든 제안이 PP-### 또는 페르소나에 연결됨
- [ ] 모든 제안에 레퍼런스 서비스 사례 있음
- [ ] 우선순위 점수 산출 및 요약표 있음
- [ ] 파이프라인 편입 여부 사용자에게 확인
