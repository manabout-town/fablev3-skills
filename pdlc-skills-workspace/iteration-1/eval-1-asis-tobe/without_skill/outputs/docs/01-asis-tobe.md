# 단골도장 — AS-IS / TO-BE 분석서

- **프로젝트**: 단골도장 (동네 카페 사장님을 위한 디지털 단골 쿠폰 서비스)
- **단계**: 1단계 (AS-IS / TO-BE)
- **작성일**: 2026-07-02
- **작성자**: 기획·개발·QA 겸임 1인
- **참조 문서**: `docs/00-project-brief.md`

---

## 1. 분석 개요

### 1.1 목적
동네 개인 카페(1인 운영)가 종이 쿠폰과 수기 도장으로 단골을 관리하는 현행 프로세스를 분석하고, 웹 기반 디지털 적립 서비스 도입 후의 목표 프로세스(TO-BE)를 정의한다. 이 문서는 2단계(요구사항 정의)의 입력이 된다.

### 1.2 분석 대상과 범위
| 구분 | 내용 |
|---|---|
| 대상 업무 | 재방문 쿠폰의 발행 → 적립 → 보상(사용) → 단골 파악 |
| 대상 사용자 | 카페 사장님(운영자), 손님(적립 고객) |
| 범위 밖 | 결제/POS 연동, 다지점 관리, 네이티브 앱 (Brief의 Out of Scope 준수) |

### 1.3 분석 방법
1인 사이드 프로젝트 특성상 별도 현장 인터뷰 없이, 일반적인 동네 카페의 종이 쿠폰 운영 관행을 기준 시나리오로 삼아 업무 흐름을 재구성했다. 실제 사장님 1명의 검증(성공 기준: 발행→적립→사용 5분 내 완주)은 QA/운영 단계에서 수행한다.

> **가정(Assumption)**: 매장은 1인 운영, 쿠폰 정책은 "도장 10개 적립 시 아메리카노 1잔 무료"를 기본형으로 한다. 정책 값은 2단계에서 설정 가능 항목으로 구체화한다.

## 2. AS-IS: 현행 프로세스 분석

### 2.1 현행 업무 흐름 (종이 쿠폰 + 수기 도장)

#### 프로세스 A. 쿠폰 발행 (신규 손님)
| # | 행위자 | 활동 | 도구 | 소요 시간(추정) |
|---|---|---|---|---|
| A1 | 사장님 | 인쇄소/문구점에서 종이 쿠폰 제작·구매 | 인쇄물 | 최초 1회 + 재고 소진 시 반복 |
| A2 | 손님 | 주문·결제 | 현금/카드 | - |
| A3 | 사장님 | "쿠폰 있으세요?" 확인 후 새 쿠폰 지급 | 종이 쿠폰 | 10~20초 |
| A4 | 사장님 | 첫 도장 날인 | 고무 도장 | 5초 |
| A5 | 손님 | 쿠폰을 지갑/주머니에 보관 | - | - |

#### 프로세스 B. 적립 (재방문)
| # | 행위자 | 활동 | 도구 | 소요 시간(추정) |
|---|---|---|---|---|
| B1 | 손님 | 주문 시 쿠폰 제시 (지갑에서 찾음) | 종이 쿠폰 | 10~30초, 못 찾으면 포기 |
| B2 | 사장님 | 쿠폰 진위·매수 육안 확인 | 육안 | 5초 |
| B3 | 사장님 | 도장 날인 (음료 잔 수만큼) | 고무 도장 | 5초 |
| B4 | 손님 | 쿠폰 회수·보관 | - | - |
| B-예외 | 손님 | "쿠폰 두고 왔어요" → 적립 포기 또는 새 쿠폰 중복 발급 | - | 단골 이탈감 유발 |

#### 프로세스 C. 보상 사용 (도장 10개 완성)
| # | 행위자 | 활동 | 도구 | 소요 시간(추정) |
|---|---|---|---|---|
| C1 | 손님 | 완성 쿠폰 제시 | 종이 쿠폰 | - |
| C2 | 사장님 | 도장 개수·위조 여부 육안 검수 | 육안 | 10~20초 |
| C3 | 사장님 | 무료 음료 제공, 쿠폰 회수·폐기 | - | - |
| C4 | 사장님 | (선택) 회수 쿠폰을 모아뒀다가 대략의 사용량 가늠 | 종이 뭉치 | 부정확 |

#### 프로세스 D. 단골 파악·마케팅
| # | 행위자 | 활동 | 현행 상태 |
|---|---|---|---|
| D1 | 사장님 | 누가 단골인지 파악 | **기억에 의존** — 얼굴은 알아도 방문 빈도·적립 현황은 데이터 없음 |
| D2 | 사장님 | 재방문 유도 (이벤트, 연락) | **불가능** — 연락 수단·근거 데이터 없음 |
| D3 | 사장님 | 쿠폰 비용·효과 측정 | **불가능** — 발행/사용량 집계 안 됨 |

### 2.2 AS-IS 흐름도 (텍스트)

```
[손님 방문] → [주문/결제] → 쿠폰 소지? ─ 예 → [쿠폰 제시] → [육안 확인] → [도장 날인]
                                │                                        │
                                └ 아니오 → [새 쿠폰 발급]                도장 10개?
                                            (분실 시 적립 이력 소멸)      ├ 아니오 → [손님 보관] → (분실/훼손 위험)
                                                                         └ 예 → [완성 쿠폰 검수] → [무료 음료] → [폐기]
                                                                                                     (데이터 미축적)
```

### 2.3 Pain Point 정리

| ID | 이해관계자 | Pain Point | 원인 | 영향(심각도) |
|---|---|---|---|---|
| P1 | 손님 | 쿠폰 분실·훼손으로 적립 이력 소멸 | 종이 매체 자체의 한계 | **상** — 적립 동기 상실, 재방문 유인 약화 |
| P2 | 사장님 | 쿠폰 위조·도장 자가 날인 가능 | 육안 검수 외 통제 수단 없음 | 중 — 무료 음료 원가 손실 |
| P3 | 사장님 | 누가 단골인지 데이터로 알 수 없음 | 적립 이력이 손님 손의 종이에만 존재 | **상** — 마케팅·보상 설계 불가 |
| P4 | 사장님 | 쿠폰 인쇄·재고 관리 비용과 수고 | 실물 소모품 의존 | 하 — 반복 비용 |
| P5 | 손님 | 쿠폰 여러 장 중복 소지, 지갑 부피 | 매장마다 별도 실물 쿠폰 | 하 — 사용성 저하 |
| P6 | 사장님 | 발행/적립/사용 통계 부재 | 기록 체계 없음 | 중 — 쿠폰 정책 효과 검증 불가 |
| P7 | 공통 | 피크타임에 쿠폰 찾기·검수로 응대 지연 | 수작업 프로세스 | 중 — 회전율 저하 |
| P8 | 사장님 | 도장 개수 실수(과다/과소 날인) 분쟁 | 수기 처리 | 하 — 신뢰 저하 |

### 2.4 현행 프로세스의 유지 요인 (왜 아직 종이인가)
- 도입 비용 0에 가깝고 학습이 필요 없다.
- 프랜차이즈용 멤버십 솔루션은 월 이용료·전용 기기(태블릿) 부담이 1인 카페에 과하다.
- 손님에게 앱 설치를 요구하는 순간 적립 참여율이 급감한다.

→ **TO-BE는 이 유지 요인을 깨지 않아야 한다**: 추가 기기 없음, 손님 앱 설치 없음, 운영 부담 최소.

## 3. TO-BE: 목표 프로세스

### 3.1 목표 상(概)
사장님은 자기 스마트폰(웹)으로 쿠폰 정책을 만들고, 손님은 앱 설치 없이 웹에서 QR 등으로 적립·쿠폰 확인을 한다. 적립 이력은 서버에 저장되어 분실이 없고, 사장님은 단골 현황을 데이터로 본다.

### 3.2 TO-BE 업무 흐름

#### 프로세스 A'. 쿠폰(적립 정책) 발행
| # | 행위자 | 활동 | AS-IS 대비 변화 |
|---|---|---|---|
| A'1 | 사장님 | 웹에서 매장 등록, 적립 정책 생성(도장 N개 → 보상) | 인쇄·재고(A1) **제거** |
| A'2 | 사장님 | 매장 QR(또는 적립 코드)을 카운터에 비치 | 실물 쿠폰 지급(A3) **대체** |

#### 프로세스 B'. 적립 (재방문 포함)
| # | 행위자 | 활동 | AS-IS 대비 변화 |
|---|---|---|---|
| B'1 | 손님 | 주문 후 카운터 QR 스캔 → 웹 페이지 진입 (앱 설치 없음) | 쿠폰 찾기(B1) **제거** |
| B'2 | 손님 | 최초 1회 간단 식별(예: 휴대폰 번호 최소 수집) | 개인정보 최소 수집 제약 준수 |
| B'3 | 사장님 | 적립 요청 확인·승인 (본인 화면에서 1탭) | 육안 검수(B2) → **시스템 검증** |
| B'4 | 시스템 | 도장 적립 기록, 손님 화면에 즉시 반영 | 날인(B3) **자동화**, 이력 서버 보존 |

#### 프로세스 C'. 보상 사용
| # | 행위자 | 활동 | AS-IS 대비 변화 |
|---|---|---|---|
| C'1 | 시스템 | 도장 N개 도달 시 사용 가능 쿠폰 자동 발급 | 완성 확인(C2) **자동화** |
| C'2 | 손님 | 웹에서 쿠폰 제시 | 실물 제시 **대체** |
| C'3 | 사장님 | 사용 처리 승인 (1탭) → 쿠폰 소멸 처리 | 회수·폐기(C3) **자동화**, 위조 원천 차단 |

#### 프로세스 D'. 단골 파악
| # | 행위자 | 활동 | AS-IS 대비 변화 |
|---|---|---|---|
| D'1 | 사장님 | 대시보드에서 적립/사용 현황, 단골(재방문) 목록 확인 | 기억 의존(D1) → **데이터 기반** |
| D'2 | 사장님 | 발행·적립·사용 통계로 정책 효과 판단 | 측정 불가(D3) **해소** |

> D2(재방문 유도 메시지 발송)는 개인정보 최소 수집 제약과 6주 일정 고려 시 **1차 범위에서 제외**를 기본안으로 하고, 2단계 요구사항 정의에서 최종 결정한다.

### 3.3 TO-BE 흐름도 (텍스트)

```
[사장님: 매장 등록 + 정책 생성 + QR 비치]  ← 최초 1회
        │
[손님 방문] → [주문] → [QR 스캔(웹)] → 최초? ─ 예 → [최소 식별 등록]
                                         │
                                         └→ [적립 요청] → [사장님 1탭 승인] → [서버 기록·화면 반영]
                                                                                  │
                                                                            도장 N개 도달?
                                                                                  ├ 아니오 → 종료 (이력 서버 보존, 분실 없음)
                                                                                  └ 예 → [쿠폰 자동 발급] → [손님 제시]
                                                                                          → [사장님 사용 승인] → [소멸 처리 + 통계 반영]
```

### 3.4 AS-IS → TO-BE 갭 분석

| 영역 | AS-IS | TO-BE | 갭 해소 수단 (시스템 요구 후보) |
|---|---|---|---|
| 적립 매체 | 종이 쿠폰 + 고무 도장 | 웹 기반 디지털 도장 | 매장 QR, 적립 트랜잭션 기록 |
| 이력 보존 | 손님 소지 실물 (분실=소멸) | 서버 영구 보존 | 손님 식별 체계(최소 수집), DB(Supabase) |
| 진위 검증 | 육안 | 시스템 검증(사장님 승인) | 적립/사용 승인 플로우 |
| 보상 처리 | 육안 계수 + 실물 폐기 | 자동 발급·소멸 처리 | 쿠폰 상태 관리(발급/사용/소멸) |
| 단골 데이터 | 없음(기억) | 대시보드 통계 | 적립/사용 집계 뷰 |
| 도입 비용 | 인쇄비(반복) | 무료 웹, 추가 기기 없음 | 반응형 웹(Next.js), 손님 무설치 |
| 응대 시간 | 쿠폰 찾기+검수 20~50초 | QR 스캔+1탭 승인 ~10초 | 최소 단계 UX |

### 3.5 TO-BE에서 하지 않는 것 (Out of Scope 재확인)
- 결제·POS 연동: 적립은 주문과 독립적으로 처리 (사장님 승인이 부정 적립 방지 수단)
- 다지점 관리: 매장 1개 = 계정 1개
- 네이티브 앱·푸시 알림: 웹으로만 제공
- 손님 상세 프로필 수집: 식별 최소 정보 외 수집하지 않음

## 4. 기대 효과와 측정 지표

| 지표 | AS-IS 기준선 | TO-BE 목표 | 측정 방법 |
|---|---|---|---|
| 적립 이력 유실률 | 분실 시 100% 유실 | 0% | 서버 보존 (구조적 해소) |
| 1회 적립 응대 시간 | 20~50초(추정) | 10초 내외 | 실측 시나리오 테스트 |
| 발행→적립→사용 완주 | 측정 불가 | 사장님 1명 5분 내 완주 | **Brief 성공 기준** |
| 핵심 여정 TC Pass율 | - | 90% 이상 | **Brief 성공 기준**, QA 단계 |
| 단골 가시성 | 0 (기억 의존) | 적립 고객 수·재방문 수 대시보드 제공 | 기능 제공 여부 |
| 쿠폰 인쇄 비용 | 반복 발생 | 0원 | 구조적 해소 |

## 5. 리스크와 전제

| ID | 리스크 | 영향 | 완화 방안 |
|---|---|---|---|
| R1 | 손님이 QR 스캔·웹 진입을 번거로워해 적립 참여율 저하 | 상 | 스캔→적립 완료까지 단계 최소화(무설치·무로그인 지향), 2단계에서 식별 방식 UX 검증 |
| R2 | 사장님 승인 단계가 피크타임 병목이 될 가능성 | 중 | 1탭 승인 설계, 승인 대기 목록 제공 |
| R3 | 휴대폰 번호 수집에 따른 개인정보 부담 | 중 | 최소 수집 원칙, 수집 항목·보관 정책을 2단계 요구사항에 명시 |
| R4 | 오프라인/통신 장애 시 적립 불가 (종이는 오프라인에서도 동작) | 하 | 장애 시 수동 보정 기능(사후 적립) 검토 |
| R5 | 1인 6주 일정 — 범위 팽창 | 상 | 본 문서의 Out of Scope 준수, D2(메시지 발송) 등 제외 기본안 유지 |

## 6. 다음 단계 (2단계: 요구사항 정의 입력 사항)

본 분석에서 도출된 요구사항 후보:
1. 매장 등록 및 적립 정책 설정 (도장 개수, 보상 내용)
2. 매장 QR 생성·표시
3. 손님 무설치 웹 적립 (최소 식별 등록 포함)
4. 사장님 적립/사용 승인 플로우 (1탭)
5. 쿠폰 자동 발급·상태 관리 (발급/사용/소멸)
6. 손님용 적립·쿠폰 조회 화면
7. 사장님용 대시보드 (적립/사용/단골 통계)
8. 개인정보 최소 수집·보관 정책 반영

미결 사항 (2단계에서 결정):
