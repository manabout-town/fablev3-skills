```markdown

## 1. 분석 개요

(누구의 어떤 프로세스인지. 예: "동네 소상공인이 단골 고객에게 재방문 쿠폰을 발행·관리하는 프로세스")

### 1.2 분석 방법
(데스크 리서치 / 사용자 관찰 / 자체 경험 / 추정 — 근거의 출처와 한계를 명시)

## 2. AS-IS 현행 프로세스

​```mermaid

    C -->|아니오| E[단계 3']
​```

### 2.2 단계별 상세

| # | 단계 | 행위자(Actor) | 사용 도구 | 소요 시간 | 문제점 |

### 2.3 Pain Point 정의

| ID | Pain Point | 발생 단계 | 근거 (정량/정성) | 원인 분석 (Why) | 심각도(H/M/L) |
|---|---|---|---|---|---|

(심각도 기준: H = 프로세스 중단 또는 큰 비용, M = 반복적 비효율, L = 불편)

## 3. TO-BE 개선 프로세스

### 3.1 설계 원칙
(TO-BE를 관통하는 원칙 2~3개. 예: "수기 입력 제거", "행위자 간 대기 시간 최소화")

### 3.2 프로세스 흐름도

### 3.4 Pain Point 해소 매핑

| PP ID | AS-IS 문제 | TO-BE 해소 방안 | 해소 수준 (완전/부분/범위 밖) |

| PP-001 | | | |

| 지표 | AS-IS | TO-BE (목표) | 산출 근거 |

## 작성 시 유의

- mermaid 코드블록의 ​``` 앞 제로폭 문자는 템플릿 표기용이다. 실제 문서에는 일반 코드블록으로 쓴다.
- PP는 5~10개가 적정. 3개 미만이면 분석이 얕은 것이고, 15개 이상이면 대상 프로세스가 너무 넓은 것이다.
- 신규 서비스의 AS-IS는 "대안 행동"이다: 사용자가 지금 문제를 어떻게 우회하는지를 프로세스로 그려라.
