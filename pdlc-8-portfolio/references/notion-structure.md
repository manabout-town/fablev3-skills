# 노션 포트폴리오 구조 · 카피 패턴 · 말투 가이드

## 1. 페이지 트리

```
📄 [서비스명] — 기획부터 운영까지 (메인, 필수 섹션 1~8)
├── 📄 01 문제 발견: AS-IS/TO-BE 분석
├── 📄 02 검증: 페르소나와 인터뷰
├── 📄 03 결정: 요구사항과 명세
├── 📄 04 계획: 마일스톤과 일정
├── 📄 05 실행: DB 설계와 MVP 구현
├── 📄 06 검증: QA와 버그
├── 📄 07 운영: 이슈 대응과 개선
└── 📄 부록: 전체 산출물 인덱스와 회고
```

## 2. 메인 페이지 — 필수 섹션 레이아웃

### §1 10초 훅
첫 화면 구성 (위→아래): 헤드라인 → 서브라인 → 히어로 GIF → 프로젝트 카드.

- 헤드라인은 서비스 이름이 아니라 문제 또는 결과로 시작한다.
  - 나쁨: "단골도장 — 카페 쿠폰 서비스 프로젝트"
  - 좋음: "종이 쿠폰 때문에 단골을 잃는 카페, 15분 걸리던 일을 2분으로 줄였다"
- 서브라인 1줄: 무엇을 어떻게 (예: "기획→구현→운영까지 혼자 완주한 6주, Next.js + Supabase").
- 프로젝트 카드 (표):

  | 기간 | 역할 | 스택 | 산출물 | 핵심 성과 |
  |---|---|---|---|---|
  | 6주 | 기획·개발·QA (1인) | Next.js, Supabase | 문서 14종 + 기능 3개 | TC Pass 94%, 처리시간 -87% |

### §2 라이브 데모
GIF마다: **볼드 1줄 캡션(무엇을 보라는 건지) + FEAT/SCR ID**. 배치는 2열 갤러리(노션 columns) 권장, 히어로 GIF는 §1에서 이미 썼으면 여기서 제외하지 말고 재배치. 장면 순서는 사용자 여정 순서를 따른다 (온보딩 → 기능 → 통합 여정 → 반응형).

### §3 30초 요약
산문 4~6문장. 형식: 문제(1~2문장) → 접근(1문장) → 만든 것(1~2문장) → 결과(1문장). 불릿 금지 — 여기만큼은 읽히는 글이어야 한다.

### §4 결과지표

| 지표 | 목표/AS-IS | 결과 | 측정 방식 |
|---|---|---|---|
| 건당 처리 시간 | 15분 | 2분 | 시뮬레이션 시나리오 실측 |
| TC 통과율 | 90% | 94% (47/50) | 실제 QA 실행 |
| 계획 대비 일정 | 6주 | 6주 + 2일 | 간트 대비 실적 |

측정/시뮬레이션 구분을 "측정 방식" 컬럼에 반드시 명시. 일정 초과·미달성 지표도 그대로 적는다 — 숨긴 티가 나는 표보다 정직한 표가 강하다.

### §5 이 프로젝트에서 봐야 할 N가지
번호 목록 3~5개, 각 항목은 "제목 1줄 + 근거 링크 + 2~3문장 설명". 노력이 아니라 판단이 보이는 순간을 고른다:
- 반박당한 가설과 방향 수정 (INS-###, decisions)
- 정책→스키마 번역 디테일 (RLS 설계)
- 경계 테스트가 실제로 잡아낸 버그 (BUG-###)
- 운영 시나리오에서 발견한 탐지 공백 (OPS-###)

### §6 문제 → 해결 매핑 (전체)

| PP | 문제 | REQ | 해결 (FEAT/POL) | 검증 (TC 결과) | 상태 |
|---|---|---|---|---|---|
| PP-001 | 쿠폰 분실 시 이력 소멸 | REQ-002 | FEAT-002 QR 적립 | TC-004~008 Pass | 해소 |
| PP-006 | 비수기 재방문 유도 불가 | REQ-006 | FEAT-006 (미구현) | - | 2차 이월 |

**모든 PP를 빠짐없이** 넣는다. 미해소·이월도 상태 컬럼으로 정직하게. 이 표의 완전성이 곧 신뢰도다.

### §7 2차 로드맵

| 순위 | 항목 | 출처 | 이유 | 규모 |
|---|---|---|---|---|
| 1 | 오류율 모니터링 도입 | OPS-001 | 탐지 수단 부재가 최대 리스크로 판명 | S |

"다음 스프린트"와 "백로그"를 구분하고, 각 항목이 어느 PP/OPS/BUG에서 왔는지 출처를 단다. 마무리 1문단: 지금 다시 시작한다면 무엇을 다르게 할지.

### §8 단계별 여정 + 부록
6박자 서사(문제→검증→결정→실행→검증·운영→다음) 각 2~3문장 + 하위 페이지 링크. 부록 페이지에 원문서 전체 인덱스와 저장소 링크.

## 3. 말투 가이드 (Writing Voice)

목표: **직접 만들어본 20~30대 개발자가 격식을 갖춰 쓴 글.** AI 생성 티가 나는 문장은 전부 걸러낸다.

### 원칙
- **1인칭 경험으로 쓴다.** 결정·실패·발견의 주어는 나다. "~하게 되었습니다"(피동) 대신 "~했다 / ~하기로 했다".
- **형용사 대신 수치와 고유명사.** "획기적으로 개선" ❌ → "15분 → 2분" ⭕. "다양한 예외 처리" ❌ → "중복 제출·만료 쿠폰·권한 없음 3가지 경로" ⭕.
- **배운 시점을 드러낸다.** 처음부터 안 것처럼 쓰지 않는다: "RLS를 나중에 붙이려다 권한 구멍을 만들 뻔했고, 이후 스키마 설계 단계에서 정책부터 쓰는 걸로 순서를 바꿨다."
- **문어체 종결(-다)로 통일하되 건조하지 않게.** 이모지는 섹션 아이콘 외 본문 금지. 느낌표 금지.
- **문장 길이를 섞는다.** 짧은 단문 뒤에 이유를 담은 긴 문장. 모든 문장이 같은 리듬이면 기계 티가 난다.

### AI 티 나는 패턴 → 교정 예
| 걸러낼 것 | 대신 |
|---|---|
| "본 프로젝트는 ~를 목표로 합니다" | "카페 사장님이 종이 쿠폰 관리에 쓰는 시간을 줄이고 싶었다" |
| "~를 통해 ~를 달성하였습니다" | "~를 도입해서 ~가 됐다" |
| "다음과 같은 성과를 거두었습니다:" + 불릿 폭탄 | 표 1개 또는 산문 2문장 |
| "완벽한", "혁신적인", "최적의" | 삭제하거나 수치로 대체 |
| 모든 문단이 3줄 + 불릿 3개 구조 반복 | 문단 길이·형식 변주 |
| "결론적으로", "요약하자면" 남발 | 접속사 없이 바로 본문 |

### 최종 voice 체크 (배포 전)
- [ ] 피동형 문장 비율이 낮은가 (표본 10문장 중 2개 이하)
- [ ] 수치 없는 성과 형용사가 없는가
- [ ] "시행착오 → 수정" 서술이 최소 2곳 있는가
- [ ] 소리 내 읽었을 때 사람이 쓴 글로 들리는가

## 4. Notion MCP 블록 변환 규칙

| 마크다운 | 노션 블록 | 주의 |
|---|---|---|
| H1/H2/H3 | heading_1/2/3 | H4 이하는 bold 단락 |
| 표 | table 블록 | 열 10개 초과 시 분할 또는 대표 행 |
| GIF | file/image 블록 업로드 | 파일 크기 제한은 demo-gif-guide.md 참조 |
| mermaid 코드블록 | code 블록 (language: mermaid) | 렌더 안 될 수 있음 — 텍스트 요약 병기 |
| 체크리스트 | to_do | |
| 핵심 결론 | callout(💡) | 페이지당 2~3개까지만 |
| 2열 GIF 갤러리 | column_list + column | |

생성 순서: 메인 페이지 → URL 확보 → 하위 페이지 → 메인에 링크 삽입. 비동기 생성이면 완료 확인 후 다음 페이지.

## 5. portfolio.md 폴백 규칙

- 페이지 경계마다 `---` + `# 제목` (노션 임포트가 페이지로 인식)
- 미지원 문법 회피: HTML 태그, 각주, 정의 목록
- GIF는 임포트에 실리지 않는다 — §2 위치에 `<!-- GIF: 01-onboarding.gif 여기에 업로드 -->` 주석을 남기고, 임포트 후 `NN-` 파일명 순서로 드래그 업로드하라고 사용자에게 안내
- 섹션 순서는 메인 페이지 §1~8과 동일
